Three subsystems, three files, one chain

The playback story splits into three layers. The first is pure — a stateless state machine and evaluator that live in WaplePolicy so they can be tested in seconds on Linux. The second is the app-side composition that reads user settings, samples the OS, and merges policy with the rest of the system (occlusion, manual pause, etc.). The third is the playlist driver, a thin orchestrator that owns elapsed time and delegates the actual scheduling math to WapleCore.PlaylistRuntime.

01

Policy state machine

File: Sources/WaplePolicy/PlaybackPolicy.swift · 692 lines · imports only Foundation. The header comment (PlaybackPolicy.swift:1–13) explains the isolation: WapleCore imports simd, which kills the Linux runner, so the policy must not depend on it. Everything in this file is a pure function over Sendable value types and can be unit-tested in milliseconds.

1.1 · The action ladder

Five discrete actions form an intensity ladder; the evaluator's contract is that higher on the ladder wins when two axes disagree.

CaserawValueWE stringMeaning
run0"run"Renderer is doing work
mute1"mute"Render but silence
pause2"pause"Halt this monitor(s)
pauseAll3"pauseall"Halt every monitor
stop4"stop"Tear down the renderer

Three things matter about this table. First, the unrecognised string falls silently to run — PlaybackAction.init(weConfigValue:) at PlaybackPolicy.swift:46–54 — because the engine's mapper at 0x140141918 does the same; a typo is "no policy", not a crash. Second, Comparable is rawValue order and the engine is the same ladder (PlaybackPolicy.swift:67–69). Third, stop is the only one that releases resources, and we reduce it to a pause — see §2.3.

1.2 · The six axes

PlaybackTrigger at PlaybackPolicy.swift:77–188 enumerates the six user-facing axes plus three derived booleans (honorsMultiMonitor, allowsMute, allowsStop) that drive the allowedActions(multiMonitor:) matrix at PlaybackPolicy.swift:156–163.

The "UI gives" column comes from scripts.js's k(e,t,a) builder — first arg is "multimonitor", second is "mute", third is "stop". The non-obvious row is audio: the UI passes a literal !1 (false) for the multimonitor argument, so it never offers pauseAll regardless of how many monitors the user has. We reproduced that mistake once; the test caught it (PlaybackPolicy.swift:144–146).

More importantly, the engine's dispatcher and the UI's offer list agree. Where the UI doesn't offer an action, the engine has no branch for it either — so picking one that's not on offer is a silent run. Two asymmetries matter: focus has no stop branch in the engine (0x14006d1fe), and pauseAll is engine-handled regardless of monitor count even though only multi-monitor configs see it in the UI.

1.3 · PlaybackPolicy value type

Six axes plus pauseVRAM: Bool at PlaybackPolicy.swift:193–284. The two named constants — weDefault at PlaybackPolicy.swift:226–234 and allRun at PlaybackPolicy.swift:241–249 — duplicate init's default arguments on purpose: the spec checker (scripts/spec/check_playback_policy.py) greps for these by name. allRun is "policy absent" — the renderer should be doing work — and is what PlaybackPolicyResolver passes when a wallpaper declares nothing.

The subscript at PlaybackPolicy.swift:262–283 lets the resolver write policy[trigger] = ... without enumerating the switch in two places.

1.4 · Inputs and outputs

PlaybackConditions at PlaybackPolicy.swift:317–392 takes 14 fields. The four mask fields (unfocusedMask, maximizedMask, fullscreenMask, allMonitorsMask) all use the bit = 1 << monitorIndex convention; the helper PlaybackConditions.mask(monitorIndices:) at PlaybackPolicy.swift:385–391 builds one from an array. The engine's shl r8d, cl at 0x140074d50 and bt eax, ecx at 0x140073a64 use the same fold, so a 5-bit reduction in the helper is intentional.

PlaybackVerdict at PlaybackPolicy.swift:397–425 has exactly three outputs:

  • stop: Bool — release the renderer. The comment at PlaybackPolicy.swift:398–399 is explicit that it shadows the other two.
  • muted: Bool — global, not per-monitor. The engine's applier at 0x140073a7b–0x140073a85 writes the same value into every instance, and we do the same.
  • pauseMask: UInt32 — bit per monitor, UInt32.max = all of them.

1.5 · The evaluator's nine-step pipeline

PlaybackEvaluator.evaluate at PlaybackPolicy.swift:443–555 is the load-bearing function. The nine numbered steps in the source are a contract — reordering any of them changes what the system does, because masks get OR'd, then later axes overwrite them, then the result-folding section collapses the lot.

Priority contract

stop ≻ displaySleep ≻ (pauseMask, mute). Stop is the strongest signal and shadows the other two. Sleep is second and forces pauseMask = .max (or stop if the axis was stop). Everything else is OR'd together at the end.

The shared applyWindowStateAxis at PlaybackPolicy.swift:559–589 is the same body for both ② and ③. Two subtleties: pause with a "spans" layout only writes .max if every monitor is covered (0x14006d162 / 0x14006d1c5); partial coverage is "the wallpaper is still visible somewhere", so it pauses nothing. pauseAll, by contrast, writes .max on any coverage (0x14006d145 / 0x14006d1a7).

1.6 · VRAM hysteresis

VRAMHysteresis at PlaybackPolicy.swift:614–692 is a separate state machine despite living in the same file. The trap to avoid: its output is stop, not pause (PlaybackPolicy.swift:597–598). The flag bit (10) is cmovne'd at the same 0x14006d407 site as the external stop request, and the verdict-folding step treats it identically. The name pausevram in WE is a misnomer we reproduce verbatim because the value lives in the same config key.

Thresholds are byte-for-byte copies of the floats at 0x1404926e4, 0x1404926d4, 0x1404926a0, 0x140492888. Enter at 80% of total, sustain for 15 seconds under 75% to release, immediate release under 35% regardless of time. Two pre-engagement gates reject the sample entirely (sampleCount < 2, total outside 2049…131071 MB); under either the hysteresis state is preserved unchanged. The NaN subtlety at PlaybackPolicy.swift:665–668 is real: comiss sets CF on unordered, and we must use used >= x not !(used < x) to land in the release path that the engine does.

Unwired

VRAMHysteresis is a model with no feeder. The macOS side would need a MTLDevice.currentAllocatedSize poller — a separate, desktop-only change that hasn't been made. Until that lands, PlaybackConditions.vramPressure stays false by default (PlaybackObservers.swift:128–131).

02

Runtime composition

Three files cooperate at the app layer. Sources/Waple/PlaybackPolicyRuntime.swift holds the global settings and resolver; Sources/Waple/PlaybackPolicyComposition.swift holds the merge with the rest of the system and the edge trackers; Sources/Waple/PlaybackObservers.swift (referenced but not exhaustively covered) is where the OS-sampling logic for the conditions builder lives.

2.1 · The two policy planes

The fundamental shift from stage 1 to stage 2 — documented in the file header at PlaybackPolicyRuntime.swift:7–33 — is recognising that the actual source of the policy is the global user setting, not project.json. A grep of the local corpus of 191 wallpapers found zero that declared any of the six axes; the values WE itself ships with in config.json match PlaybackPolicy.weDefault exactly. The per-wallpaper playbackProperties dict is a layered override on top, not the primary declaration.

GlobalPlaybackSettings at PlaybackPolicyRuntime.swift:39–75 wraps UserDefaults with a waple.playback. prefix and reuses the WE key names (PlaybackPolicyRuntime.swift:37–38) so a future import path doesn't need a mapping table. The crucial detail is at PlaybackPolicyRuntime.swift:60: object(forKey:), not bool(forKey:), because the latter collapses "unset" and false, which silently rots if the default ever flips.

PlaybackPolicyResolver at PlaybackPolicyRuntime.swift:79–101 is the merge. effective(global:declaring:) at PlaybackPolicyRuntime.swift:86–93 takes the global policy and overlays only axes the wallpaper declared — empty strings and missing keys are skipped, which reproduces WE's ""-injection behaviour. verdict(for:conditions:global:) at PlaybackPolicyRuntime.swift:96–100 returns non-optional PlaybackVerdict because there is no longer a "policy absent" short-circuit — absence means "use the global", not "use .running".

2.2 · Window-derived masks

PlaybackMasks at PlaybackPolicyRuntime.swift:113–197 is pure: it consumes a snapshot of windows from DesktopVisibilityMonitor.currentSnapshots() and produces the three masks the conditions need. Three details matter.

  • Coverage with a tolerance — covers(_:_:tolerance:) at PlaybackPolicyRuntime.swift:140–146 is bidirectional (the window can be larger or smaller by 4pt) because macOS shadow rendering and integer rounding shift window bounds by a few points. A one-sided window contains target check would over-trigger on multi-monitor windows.
  • Foreign window filter — isForeignWindow(_:currentProcessId:) at PlaybackPolicyRuntime.swift:130–133 shares the "another process" test with DesktopVisibilityMonitor.isBlocking but not the "is this blocking the desktop" intent; that's a separate question.
  • Visible vs full frame — maximized uses visibleFrame (excludes menu bar and dock) and fullscreen uses frame (covers everything). The two masks are usually disjoint on a clean machine and merge only when the layout is non-per-monitor, in ① of the evaluator.

2.3 · The OR junction — and the stop→pause reduction

RenderPauseComposition at PlaybackPolicyComposition.swift:23–140 is the merge point. The system has two independent stop paths: PauseGate (the occlusion/manual/system-sleep aggregator) and the playback policy. The decision was to keep both layers and OR them, confined to one file (PlaybackPolicyComposition.swift:6–21) so the rest of the code doesn't have to think about it.

Decision at PlaybackPolicyComposition.swift:25–40 is the per-renderer output. paused is the OR of the global pause and the per-monitor policy signal. policyWantsStop and policyWantsMute are carried so the edge trackers and the mute aggregator can consume them later.

The non-obvious decision is at PlaybackPolicyComposition.swift:30–33 and the long block at 42–87: verdict.stop is reduced to a pause before it leaves the composition layer. Three alternatives were considered and rejected (PlaybackPolicyComposition.swift:46–49):

  1. Full teardown + remount on stop. The dominant trigger is displaySleep, which the default policy sets to stop. Without the reduction, every sleep/wake cycle tears down the renderer and remounts it. The remount path is throws and has no recovery in a desktop-with-no-renderer scenario, so a single failure yields a black wallpaper that the library cannot restore on its own.
  2. Partial resource release (scene FBO pool, etc.). Sound in principle, but the pool is ordered to support motion-blur persistence across frames and we have no way to verify its behaviour from inside this container. We don't take speculative gains on a GPU path.
  3. The reduction we chose. Visually identical to a real stop (the screen is paused either way), loses only memory residency, and the lost memory is reclaimed for free by the OS during sleep.
stopIsReducedToPause = true

This is named at PlaybackPolicyComposition.swift:87 so the assertion can pin it. The settings UI tells the user "this option is currently a pause"; the saved value is still the WE string "stop" for future compatibility. Reverting this requires a measured pass on real hardware: 100 sleep/wake cycles with zero mount failures and a confirmed remount cost that doesn't degrade wake latency.

Two decideAll overloads at PlaybackPolicyComposition.swift:105–127 differ in whether a single verdict is shared across all renderers or computed per-project. The per-project overload is what we use: per-screen wallpapers declare independently, so a single shared verdict would let wallpaper A's policy stop wallpaper B. Index = monitor index is a load-bearing invariant — AppDelegate.renderers is built in screenViews order (PlaybackPolicyComposition.swift:102–104).

wantsGlobalMute(_:) at PlaybackPolicyComposition.swift:137–139 is OR, not AND, because WE's mute is global: a single screen saying "be quiet" should silence everything, and a single screen saying "go ahead" doesn't override the others. The error direction matters: wrong means one screen plays its sound when it shouldn't, not "everything stopped when it shouldn't".

2.4 · Edge trackers

The conditions poll at 1 Hz, so calling renderers[i].pause() every tick would be an idempotent storm. PerRendererPauseState at PlaybackPolicyComposition.swift:148–172 holds the last applied boolean per renderer and emits only the changes. The reset() method at PlaybackPolicyComposition.swift:169 exists because a renderer set change (monitor hot-plug, project rebuild) breaks the index-to-screen correspondence — re-diffing is the only safe move.

AppliedFlag at PlaybackPolicyComposition.swift:180–196 is the same idea for the global mute bit, with one twist: its initial value is nil, not false. change(to:) at PlaybackPolicyComposition.swift:186–190 returns the new value the first time regardless of what that value is. Starting at false would skip the first setPolicyMuted(true) on a fresh renderer swap, and the policy mute would silently vanish during a rebuild.

2.5 · The composition call site

AppDelegate.applyPlaybackPolicy at AppDelegate.swift:910–961 is the entire wiring. Worth tracing in order:

  1. Renderer/project parity check at AppDelegate.swift:913–917 — if the two arrays are out of sync, reset() both edge trackers and exit. Acting on a mismatched index would apply policy to the wrong screen.
  2. Build conditions at AppDelegate.swift:919–945 — the comment at AppDelegate.swift:940–944 documents the isOtherAppPlaying subtraction: CoreAudio's kAudioDevicePropertyDeviceIsRunningSomewhere can't filter out our own session, so when we're playing audio the axis is effectively disabled for that tick. The error direction is "didn't notice another app's audio", not "stopped ourselves" — the safe one.
  3. Resolve and decide at AppDelegate.swift:944–949 — global settings read, per-project verdicts computed, the OR with pauseGate happens here.
  4. Apply per-renderer pauses at AppDelegate.swift:950–953 — only the changed indices get the call.
  5. Apply global mute at AppDelegate.swift:955–960 — same idea via AppliedFlag. The setter is setPolicyMuted(_:), added in stage 3①.
03

Playlist driver

File: Sources/Waple/PlaylistDriver.swift · 173 lines. The driver is the app-side consumer of WapleCore.PlaylistRuntime; the actual scheduling math (per-screen elapsed, "what's next", "should I advance") lives in core and is tested in the Linux lane. The driver owns wall-clock, persistence, and the four app-level concerns: bridging our schema to WE's, knowing which screens to drive, refusing to let a user pick get clobbered, and persisting at a sensible cadence.

3.1 · The bridge

PlaylistSettingsBridge at PlaylistDriver.swift:21–40 is the single translation point between PlaylistStore (our schema) and PlaylistSettings (WE's). The mapping is four rows:

Our fieldWE fieldNote
enabled == falsemode = .neverWE's parser zeros delay on never, tripping the 0.01min guard. Same observable behaviour as "auto-advance off".
enabled == truemode = .timerDefault mode id = 1.
shuffleorder = .random | .sortedWE's shuffled mode is also a draining shuffle-back.
intervalMinutesdelay (Float, min 0.01)Our integer is a subset of WE's float. We clamp to 1 minimum.

The comment at PlaylistDriver.swift:30–31 documents the four WE keys we leave off: videoSequence, beginFirst, playIntro, and the transition* family. The reason is the same in each case: the spec layer models them, but the storage schema and UI to expose them don't exist yet. videoSequence is the one to watch — if it's ever enabled, the runtime will pause the timer when a video is current and notify nobody, so video wallpapers will never advance on their own. The playIntro value defaults to false for the same reason. Transitions are hard-disabled at the runtime level (PlaylistDriver.swift:36) because there is no transition renderer; the engine's -1 = "no transition" is what actually happens on screen.

3.2 · Time ownership

The driver is the only place that knows "what time is it now". The runtime takes deltas; the driver feeds them in. The 5-second clamp in PlaylistSettings.clampedTickDelta (in core) handles sleep and clock skew — a 5-hour sleep would not advance a wall to its 5-hour mark — and the driver doesn't have to think about it.

3.3 · Lifecycle

Five public methods, called in this order by AppDelegate:

  • sync(enabled:intervalMinutes:shuffle:ids:screenKeys:currentEntryId:) at PlaylistDriver.swift:91–110 — push the new store contents into the runtime, set the active screens, and detect user picks via currentEntryId. The screenKeys filter at AppDelegate.swift:790–796 excludes screens the user pinned via monitors.json; we never touch those.
  • tick(now:isPaused:isVideo:) at PlaylistDriver.swift:118–128 — call every second. Computes the delta since the last tick, hands it to the runtime, and returns the screen keys that want to advance. Doesn't advance anything. The isVideo default is { _ in false } because the two runtime gates that consult it (0x140076d81 and 0x140076d87) only activate when videoSequence or the intro latch is true, and the bridge disables both. When UI for those lands, this default needs to become a real value.
  • advance(screenKey:now:apply:) at PlaylistDriver.swift:137–151 — given a screen that wants to advance, walk the runtime's candidate list, hand each to the apply closure, and commit the first one that returns true. Bounded to one full lap of entryIds so a single deleted item doesn't permanently freeze the playlist. The persist(now:) call inside the success branch at PlaylistDriver.swift:146 is the only time we persist in response to a change, because that's when elapsed resets to zero — and if we lose that state, restoration can't recover.
  • adopt(entryId:screenKey:) at PlaylistDriver.swift:154–156 — the user just picked a wallpaper, so reset the clock without advancing.
  • persist(now:) at PlaylistDriver.swift:162–165 and the throttled persistIfDue(now:) at PlaylistDriver.swift:167–171 — write the per-screen elapsed map to PlaylistStateTimeStore. The 60-second throttle (PlaylistDriver.swift:61) balances disk wear against the worst-case loss window on a hard kill.

3.4 · The first-sync baseline

The hasSynced flag at PlaylistDriver.swift:73 and the guard at PlaylistDriver.swift:105–107 exist because runtime.restoreElapsed(stateTime.elapsedByScreen) at PlaylistDriver.swift:80 reloads the per-screen elapsed times from disk on startup. If the very first sync also called adopt, the restored values would be overwritten with zero and persistence would be useless. The first sync establishes the baseline; the second-and-later syncs detect user picks and adopt them.

3.5 · Driver ↔ runtime ↔ AppDelegate

The three-way split is by responsibility:

  • PlaylistRuntime (WapleCore) decides whether to advance, the next candidate index, and the elapsed accumulator. It's a value type; tests are deterministic.
  • PlaylistDriver owns wall-clock, schema bridging, user-pick detection, and persistence. It translates between the runtime and the app.
  • AppDelegate owns the I/O — calling apply with the new wallpaper id, calling renderers[i].setWallpaper or whatever the mount path is. It's the only file excluded from Linux typechecking, so the reasoning stays in the driver and the testable core.

The call sites in AppDelegate confirm this split: sync at AppDelegate.swift:785, tick at AppDelegate.swift:799, advance at AppDelegate.swift:806, advance (on user pick) at AppDelegate.swift:817, advance (synchronous from a settings change) at AppDelegate.swift:838, and persist at AppDelegate.swift:1582 on shutdown.

What isn't wired yet

Six PlaybackConditions fields are always defaulted to false because the conditions builder doesn't pass them (PlaybackObservers.swift:127–132):

FieldFlag bitWould need

Two more gaps are architectural, not just observational:

  • layout is always .perMonitor — the conditions builder hardcodes it at PlaybackObservers.swift:115 because Waple doesn't yet have stretch/clone monitor configurations. When it does, that line is the only thing that needs to change to engage the layout branch in the evaluator.
  • Audio subtraction is coarser than WE — documented at AppDelegate.swift:940–944. WE enumerates WASAPI sessions to filter out its own; CoreAudio's isRunningSomewhere is one bit per device, so when we're playing audio the entire axis is suppressed for that tick. The error direction is the safe one, but the gap is real.

Invariants not to break

  • Renderer index = monitor index. PlaybackPolicyComposition.swift:102–104. If the order changes, the per-renderer decisions land on the wrong screen.
  • Evaluator step order. The nine steps in PlaybackPolicy.swift:443–555 are a contract, not a refactor target. The disassembly anchors in the comments are the proof.
  • AppliedFlag initial nil. A false default would silently drop the first mute on a renderer swap.
  • Playlist screenKeys excludes user-pinned screens. The driver's screenKeys parameter must remain a filtered subset (AppDelegate.swift:790–796). Including pinned screens lets the playlist override a user choice.
  • First sync doesn't adopt. Otherwise the restored elapsed times are zeroed on the first tick after launch.
